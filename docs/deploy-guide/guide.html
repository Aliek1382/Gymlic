چرا فرانت بیلد می‌خواهد و بک‌اند نه

سرور فایل‌های PHP را مستقیم می‌خواند؛ آنچه آپلود می‌کنید همان است که اجرا می‌شود. ولی مرورگر فایل‌های .tsx را نمی‌فهمد — باید اول به HTML و JavaScript ساده تبدیل شوند. این کار را npm run build انجام می‌دهد و خروجی‌اش در پوشه‌ی out/ می‌نشیند. آنچه روی هاست می‌رود out/ است، نه کد اصلی. چون هاست اشتراکی Node ندارد، این تبدیل روی سیستم شما انجام می‌شود.

یک‌بار برای همیشه

برای بیلد، کتابخانه‌ها (React، Next، Tailwind و…) لازم‌اند. این‌ها در گیت نیستند و با npm install دانلود می‌شوند. فقط وقتی دوباره لازم است که package.json عوض شود.

چرا این ترتیب

هر لایه به لایه‌ی زیرش تکیه می‌کند. اگر صفحه‌ی جدید زودتر از اندپوینتش بالا برود، چند ثانیه‌ای روی سایت زنده است در حالی که پشتش چیزی نیست و هر کس بازش کند خطا می‌گیرد. برعکسش بی‌ضرر است: اندپوینت جدید تا آمدن فرانت فقط بلااستفاده می‌ماند. جدولی هم که ساخته نشده باشد یعنی اندپوینت تازه‌رسیده در همان اولین درخواست می‌شکند.

بخش ۳

دستورها و دامنه‌ی هر کدام

سه حالت اسکریپت، و اینکه هر کدام دقیقاً چه می‌کند.

دستورچه می‌کند
deploy\deploy.bat فرانت را بیلد و آپلود می‌کند. فایل‌های اضافه را پاک می‌کند.
deploy\deploy.bat api فقط فایل‌های PHP. بیلد نمی‌گیرد و هیچ‌وقت چیزی پاک نمی‌کند.
deploy\deploy.bat all بیلد ← بک‌اند ← فرانت، به همین ترتیب.
deploy\deploy.bat all -y همان، بدون پرسیدن تأیید.

چه چیزی محافظت شده است

فایلچرا
config.php رمز واقعی دیتابیس داخلش است و نسخه‌ی گیت CHANGE_ME دارد. در ماسک است و هیچ‌وقت آپلود نمی‌شود.
public/uploads/ آواتارها و لوگوها. آپلود بک‌اند اصلاً حذف نمی‌کند، پس امن است.
out/.htaccess اگر بیلد نسازدش، اسکریپت متوقف می‌شود — بدون آن لینک‌های دعوت /join/ می‌شکنند.
آپلود فرانت حذف می‌کند

هر چیزی که در out/ نباشد از public_html پاک می‌شود — نه فقط فایل‌های بیلد قبلی. گزینه‌ی Compress پنل، فایل zip را داخل همان پوشه می‌سازد، پس بک‌آپی که آنجا بگیرید با اولین استقرار بعدی از بین می‌رود. بک‌آپ را دانلود کنید یا بیرون از public_html بسازید.

بخش ۴

نقشه‌ی فایل‌ها روی هاست

وقتی لازم شد دستی سراغ چیزی بروید، اینجا را نگاه کنید.

/domains/gymlic-panel.ir/public_html/     ← سایت (خروجی بیلد)
  index.html, _next/, login/, ...         همه ساخته‌ی npm run build
  .htaccess                               مسیریابی /join/ و کش

/domains/api.gymlic-panel.ir/public_html/ ← API
  .htaccess                               هر درخواست را به public/index.php می‌برد
  config.php                              رمز دیتابیس — فقط اینجا
  public/index.php                        روتر و فهرست اندپوینت‌ها
  public/uploads/                         آواتارها و لوگوها
  src/                                    کنترلرها و کلاس‌ها
  schema/                                 فقط مرجع — اجرا نمی‌شود
قاعده‌ی طلایی چیدمان

index.php انتظار دارد config.php و src/ کنار پوشه‌ی public/ باشند، یعنی یک سطح بالاتر از خودش. اگر REMOTE_API به پوشه‌ای با چیدمان دیگر اشاره کند، آپلود کنارش می‌نشیند و API با خطای ۵۰۰ می‌افتد چون config.php را پیدا نمی‌کند.

فایل تنظیمات استقرار

deploy\deploy.config.bat روی سیستم شماست و در گیت نیست. پنج مقدار دارد: 

set "WINSCP_COM=E:\PROGRAMS\WinSCP\WinSCP.com"
set "SESSION=gymlic-deploy"
set "REMOTE_FRONT=/domains/gymlic-panel.ir/public_html"
set "REMOTE_API=/domains/api.gymlic-panel.ir/public_html"
set "API_URL=https://api.gymlic-panel.ir"

رمز FTP اینجا نیست — در خود WinSCP ذخیره شده و اسکریپت با نام سشن صدایش می‌زند.

بخش ۵

بک‌آپ

بیشتر پروژه در گیت است. فقط سه چیز غیرقابل‌بازیابی‌اند.

چه چیزیچطورکِی
دیتابیس phpMyAdmin ← Export ← Custom ← SQL ← zipped قبل از هر تغییر اسکیما، و هفتگی وقتی کاربر واقعی داشتید
config.php با WinSCP دانلودش کنید یک‌بار، و بعد از هر تغییر رمز دیتابیس
public/uploads/ کل پوشه را با WinSCP بکشید روی سیستم وقتی کاربران شروع به آپلود عکس کردند

چیزهایی که لازم نیست

  • کد PHP بک‌اند و کد فرانت — در گیت‌هاب هستند
  • schema.sql و seed.sql — در گیت‌هاب هستند
  • محتویات public_html سایت — با یک بیلد دوباره ساخته می‌شود
بک‌آپ روی همان هاست بک‌آپ نیست

فایل خروجی را دانلود کنید. اگر روی همان سرور بماند و سرور مشکل بخورد، بک‌آپ هم با آن می‌رود.

دیدن خطای واقعی پشت صفحه‌ی سفید ۵۰۰

صفحه‌ی ۵۰۰ عمداً جزئیات را پنهان می‌کند. کنار public/index.php فایلی به نام debug.php بسازید:

بعد <API>/public/debug.php را باز کنید تا پیام واقعی با نام فایل و شماره‌ی خط را ببینید.

بعد از عیب‌یابی پاکش کنید

این فایل مسیر کامل فایل‌های سرور را به هر بازدیدکننده‌ای نشان می‌دهد.

علامت‌های شناخته‌شده

'cp' is not recognized as an internal or external command

دستور یونیکسی در اسکریپت بیلد. در خود پروژه اصلاح شده — اگر دیدیدش یعنی نسخه‌ی قدیمی دارید؛ git pull بزنید.

\WinSCP\WinSCP.com was unexpected at this time

پرانتز موجود در مسیر WinSCP. در اسکریپت اصلاح شده؛ اگر برگشت، مسیر را بدون پرانتز بنویسید — مثلاً C:\PROGRA~2\... به‌جای Program Files (x86).

Cannot open site folder or workspace

WinSCP در تشخیص نام سایت به بزرگی و کوچکی حروف حساس نیست. اگر هم‌زمان سایتی به نام gymlic و پوشه‌ای به نام Gymlic داشته باشید، به پوشه می‌خورد. نام سایت را یکتا کنید و SESSION را به‌روز کنید.

These files have Windows line endings

محافظ اسکریپت جلوی آپلود را گرفته. درخت کاری قبل از قوانین خط‌پایان بیرون کشیده شده. از ریشه‌ی پروژه: git rm --cached -r . و بعد git reset --hard.

Your local changes would be overwritten by merge

روی فایل‌هایی که دست نزده‌اید. reset --hard تنهایی حلش نمی‌کند چون تناقض در خود commit است. به نسخه‌ی ریموت reset کنید: git fetch origin و بعد git reset --hard origin/<branch>.

No such file or directory: .../public_html

پوشه‌ی مقصد روی هاست وجود ندارد. سراغ بخش ۷ بروید.

خطای ۵۰۳ بعد از چند بار ۵۰۰

LiteSpeed برنامه‌ای را که پشت سر هم خطا داده موقتاً مسدود می‌کند. یکی دو دقیقه صبر کنید؛ خودش آزاد می‌شود و خطای واقعی دوباره ظاهر می‌شود.

سایت بالا می‌آید ولی «ارتباط با سرور برقرار نشد»

فرانت سالم است و API جواب نمی‌دهد. <API>/health را باز کنید — مشکل آنجاست، نه در فرانت.

بخش ۷

بازیابی کامل بک‌اند

اگر فایل‌های API به هر دلیلی از بین رفتند. دیتابیس جداست و دست نمی‌خورد.

۱
پوشه‌ی مقصد را بسازید

در WinSCP داخل /domains/api.gymlic-panel.ir/ پوشه‌ای به نام public_html با دسترسی 755 بسازید. اگر کل پوشه‌ی دامنه نیست، اول دامنه را در DirectAdmin ← Domain Setup دوباره اضافه کنید و گواهی SSL را هم دوباره صادر کنید.

۲
فایل‌ها را از گیت برگردانید
deploy\deploy.bat api

همه‌ی PHP، .htaccess، schema/ و پوشه‌ی public/uploads/ ساخته می‌شوند.

۳
config.php را دستی بسازید

تنها فایلی که از گیت نمی‌آید. در WinSCP راست‌کلیک ← New ← File با نام config.php در ریشه‌ی public_html: 

<?php
declare(strict_types=1);

return [
    'db' => [
        'host'    => 'localhost',
        'name'    => 'gymlicpa_____',   // MySQL Management
        'user'    => 'gymlicpa_____',   // MySQL Management
        'pass'    => '_____________',   // رمز همان کاربر
        'charset' => 'utf8mb4',
    ],

    'cors_origins' => ['https://gymlic-panel.ir'],

    'session_ttl_seconds' => 60 * 60 * 24 * 30,

    'uploads' => [
        'dir'        => __DIR__ . '/public/uploads',
        'public_url' => '/uploads',
        'max_bytes'  => 8 * 1024 * 1024,
    ],
];

نام دیتابیس و کاربر را از DirectAdmin ← MySQL Management بردارید. اگر رمز را به یاد ندارید، همان‌جا عوضش کنید — جای دیگری استفاده نمی‌شود.

وقتی کاربر واقعی داشتید

تا وقتی سایت کاربر واقعی ندارد، تست مستقیم روی نسخه‌ی زنده اشکالی ندارد. بعد از آن ارزش دارد یک ساب‌دامین جدا با دیتابیس مستقل بسازید و اول آنجا مستقر کنید — یک deploy.config.bat دوم با مسیرها و API_URL آن محیط کافی است. از آن به بعد استقرار روی نسخه‌ی زنده فقط بعد از سبز شدن نسخه‌ی تست انجام می‌شود.
