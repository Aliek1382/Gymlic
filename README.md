# جیم‌لیک (Gymlic)

پلتفرم SaaS مدیریت باشگاه، مربی و ورزشکار — Next.js 15 (App Router) + TypeScript + Tailwind CSS + shadcn/ui، روی یک API با PHP و MySQL.

هر دو بخش برای هاست اشتراکی معمولی (cPanel/DirectAdmin) ساخته شده‌اند: فرانت به‌صورت
static export بیلد می‌شود و بک‌اند PHP خام بدون Composer است. نه Node لازم است،
نه PostgreSQL، نه WebSocket.

## راه‌اندازی

۱. بک‌اند را بالا بیاورید (راهنمای کامل در `backend-php/README.md`):

   ```bash
   mysql -u root -e "CREATE DATABASE gymlic_dev CHARACTER SET utf8mb4"
   mysql -u root gymlic_dev < backend-php/schema/schema.sql
   mysql -u root gymlic_dev < backend-php/schema/seed.sql   # تمرین‌ها و غذاهای آماده
   ./backend-php/dev-server.sh                              # http://127.0.0.1:8099
   ```

۲. آدرس API را برای فرانت تنظیم کنید:

   ```bash
   cp .env.example .env.local
   ```

۳. نصب و اجرا:

   ```bash
   npm install
   npm run dev
   ```

   سپس آدرس [http://localhost:3000](http://localhost:3000) را باز کنید.

## استقرار (هاست اشتراکی)

استقرار دو تکه دارد: بک‌اند PHP و خروجی استاتیک فرانت.

**بک‌اند** طبق `backend-php/README.md` آپلود و تنظیم می‌شود (دیتابیس، `config.php`،
و ساب‌دامین یا پوشه‌ی `/api`). بعد از آپلود، `‎<آدرس API>/health` باید
`{"ok":true}` برگرداند.

**فرانت** به‌صورت **static export** بیلد می‌شود: خروجی چند فایل HTML/JS ساده است
و روی هاست به Node نیازی ندارد. چون بیلد به Node نیاز دارد و هاست اشتراکی آن را
ندارد، بیلد را روی سیستم خودتان بگیرید و فقط خروجی را آپلود کنید.

```bash
npm run build      # خروجی در out/ ساخته می‌شود؛ .htaccess و serve.json کنارش کپی می‌شوند
npm run preview    # پیش‌نمایش محلی همان خروجی روی http://localhost:3000
```

`npm run preview` دقیقاً همان فایل‌هایی را سرو می‌کند که آپلود می‌شوند، پس بهترین
راه تست قبل از استقرار است — و چون `deploy/serve.json` همان rewrite مربوط به
`/join/` را تکرار می‌کند، لینک‌های دعوت هم محلی قابل آزمایش‌اند.

سپس محتویات `out/` (به‌همراه فایل مخفی `.htaccess`) را با FTP در `public_html`
آپلود کنید.

- متغیر `NEXT_PUBLIC_API_URL` در زمان **بیلد** داخل باندل درج می‌شود، نه در زمان
  اجرا. پس هر بار که تغییرش دادید باید دوباره بیلد و آپلود کنید:

  ```bash
  NEXT_PUBLIC_API_URL=https://api.yourdomain.com npm run build
  ```

- دامنه‌ی سایت باید در `cors_origins` داخل `backend-php/config.php` باشد، وگرنه
  مرورگر درخواست‌ها را بلاک می‌کند.
- اگر سایت روی `https` است، API هم باید روی `https` باشد؛ وگرنه مرورگر
  درخواست‌های ناامن را بلاک می‌کند.
- `deploy/.htaccess` مسیر `/join/<code>` را به شل صادرشده هدایت می‌کند تا
  لینک‌های دعوت که بیرون از برنامه به اشتراک گذاشته می‌شوند نشکنند.
- `deploy/serve.json` همان قانون را برای `npm run preview` تکرار می‌کند.

### به‌روزرسانی‌های بعدی

روی هاست هیچ کدی اجرا نمی‌شود، پس هر استقرار فقط یعنی «پوشه‌ی روی هاست را شبیه
پوشه‌ی محلی کن». بسته به اینکه چه چیزی عوض شده، یکی از این سه کار لازم است:

| چه چیزی عوض شده | چه کاری لازم است | بیلد لازم است؟ |
| --- | --- | --- |
| فرانت (صفحه، کامپوننت، استایل) | بیلد و آپلود `out/` در `public_html` | بله |
| بک‌اند (فایل‌های `.php`) | جایگزینی همان فایل‌ها روی هاست | خیر |
| دیتابیس (جدول یا ستون جدید) | اجرای همان `ALTER`/`CREATE` در phpMyAdmin | خیر |

برای مورد سوم **هرگز `schema/schema.sql` را دوباره ایمپورت نکنید**؛ روی جدول‌های
موجود خطا می‌دهد و تغییری هم اعمال نمی‌کند.

`deploy/deploy.bat` (ویندوز + [WinSCP](https://winscp.net)) دو مورد اول را
انجام می‌دهد. یک‌بار `deploy/deploy.config.example.bat` را به
`deploy/deploy.config.bat` کپی و پر کنید، و اتصال FTP را در خود WinSCP ذخیره
کنید (`Session → Save` با تیک ذخیره‌ی رمز) — رمز در همان‌جا می‌ماند، نه در فایلی
داخل پروژه.

```
deploy\deploy.bat          فرانت: بیلد + آپلود (حالت معمول)
deploy\deploy.bat api      بک‌اند PHP
deploy\deploy.bat all      هر دو
```

دو چیز هیچ‌وقت آپلود یا حذف نمی‌شوند: `backend-php/config.php` (رمز واقعی
دیتابیس داخلش است و نسخه‌ی داخل گیت هنوز `CHANGE_ME` دارد) و
`backend-php/public/uploads/` (آواتارها و لوگوهای آپلودشده). در مقابل، آپلود
فرانت فایل‌های قدیمی را پاک می‌کند، چون هر بیلد نام فایل‌های JS/CSS خود را عوض
می‌کند و بدون پاک‌سازی، هر استقرار یک نسخه‌ی مرده از برنامه روی هاست جا می‌گذارد.

کش مرورگر مشکلی ایجاد نمی‌کند: `deploy/.htaccess` فایل‌های HTML را
`no-cache` و فایل‌های هش‌دار را یک‌ساله کش می‌کند، پس کاربر بلافاصله نسخه‌ی جدید
را می‌بیند.

#### فیچری که هر سه لایه را لمس می‌کند

یک فیچر کامل (مثلاً خرید اشتراک) معمولاً هم‌زمان جدول جدید، کنترلر و روت جدید، و
صفحه‌ی جدید می‌خواهد. ترتیب مهم است، چون لایه‌ی بالاتر به لایه‌ی پایین‌تر تکیه
می‌کند:

1. **دیتابیس** — `ALTER`/`CREATE` را در phpMyAdmin اجرا کنید. اسکریپت دیتابیس را
   لمس نمی‌کند؛ این قدم همیشه دستی است.
2. **بک‌اند و فرانت** — `deploy\deploy.bat all`.

خود `all` هم بک‌اند را قبل از فرانت آپلود می‌کند: اگر صفحه‌ی جدید زودتر بالا
برود، چند ثانیه‌ای روی سایت زنده است در حالی که اندپوینتش هنوز نرسیده و هر کس
بازش کند خطا می‌گیرد. برعکسش بی‌ضرر است — اندپوینت جدید تا آمدن فرانت بلااستفاده
می‌ماند.

#### وقتی استقرار کار نمی‌کند

هر کدام از این‌ها یک بار روی یک هاست واقعی اتفاق افتاده است. علامت را پیدا
کنید، نه علت را حدس بزنید.

**`\WinSCP\WinSCP.com was unexpected at this time`**
مسیر WinSCP در `deploy.config.bat` پرانتز دارد و اسکریپت آن را جای دیگری چاپ
می‌کرد. این در خود اسکریپت اصلاح شده؛ اگر دوباره دیدیدش یعنی مسیر را در جای
تازه‌ای با پرانتز گذاشته‌اید.

**`Cannot open site folder or workspace`**
WinSCP در تشخیص اسم سایت به بزرگی و کوچکی حروف حساس نیست. اگر هم‌زمان یک سایت
به اسم `gymlic` و یک **پوشه‌ی سایت** به اسم `Gymlic` داشته باشید، `open gymlic`
به پوشه می‌خورد و شکست می‌خورد. اسم سایت را یکتا کنید و `SESSION` را به‌روز کنید.

**`These files have Windows line endings and would break the API`**
محافظ پیش از آپلود جلوی شما را گرفته است. درخت کاری قبل از اضافه شدن قوانین
`.gitattributes` بیرون کشیده شده. از ریشه‌ی پروژه:

```
git rm --cached -r .
git reset --hard
```

**`Your local changes to the following files would be overwritten by merge`
روی درختی که دست نزده‌اید**
همان مسئله از سمت گیت: فایل با CRLF در ایندکس ذخیره شده ولی `.gitattributes`
انتظار LF دارد، پس همیشه «تغییریافته» دیده می‌شود. `reset --hard` تنهایی
درستش نمی‌کند، چون تناقض در خود commit است. به نسخه‌ی ریموت reset کنید:

```
git fetch origin
git reset --hard origin/<نام برنچ>
```

**بعد از آپلود موفق، سایت `500` می‌دهد**
صفحه‌ی ۵۰۰ عمداً جزئیات را پنهان می‌کند. یک `debug.php` کنار `index.php`
بسازید تا خطای واقعی را ببینید، و **بعد از عیب‌یابی پاکش کنید**:

```php
<?php
ini_set('display_errors', '1');
error_reporting(E_ALL);
require __DIR__ . '/index.php';
```

رایج‌ترین علتش این است که `REMOTE_API` به پوشه‌ای اشاره می‌کند که چیدمانش با
چیدمان مخزن یکی نیست. `index.php` انتظار دارد `config.php` و `src/` **کنار**
پوشه‌ی `public/` باشند — یعنی `REMOTE_API` باید همان پوشه‌ای باشد که محتویات
`backend-php/` در آن می‌نشیند. اگر قبلاً دستی با چیدمان دیگری آپلود کرده باشید
(مثلاً محتویات `public/` مستقیم در `public_html` و `config.php` یک سطح بالاتر)،
آپلود اسکریپت کنار آن می‌نشیند و `config.php` پیدا نمی‌شود.

**۵۰۳ بعد از چند بار ۵۰۰**
LiteSpeed برنامه‌ای را که پشت سر هم خطا داده موقتاً مسدود می‌کند. یکی دو دقیقه
صبر کنید؛ خودش آزاد می‌شود و خطای واقعی دوباره ظاهر می‌شود.

### تفاوت‌ها با نسخه‌ی سروری

چون هیچ کدی روی سرور اجرا نمی‌شود:

- `middleware.ts` حذف شده و ریدایرکت‌های نشست در لایه‌های `(dashboard)`،
  `(auth)` و `admin` سمت کلاینت انجام می‌شود.
- صفحات جزئیات شناسه را از query string می‌خوانند
  (`/athletes/profile?id=…` به‌جای `/athletes/<id>`).
- گاردهای سمت کلاینت فقط تعیین می‌کنند چه چیزی نمایش داده شود؛ **محافظ واقعی
  داده‌ها API است**، چون فایل HTML هر صفحه برای همه قابل دریافت است. هر اندپوینت
  دسترسی را خودش دوباره بررسی می‌کند.
- به‌جای Realtime سوپابیس (که روی هاست اشتراکی وجود ندارد)، اینباکس، زنگ اعلان و
  گفتگوی باز با فاصله‌ی کوتاه polling می‌شوند.

## معماری

- `app/` — مسیرهای Next.js App Router؛ گروه `(auth)` صفحات ورود/OTP/انتخاب نقش و گروه `(dashboard)` پنل اصلی را در بر می‌گیرد.
- `features/authentication/` — فلوی کامل احراز هویت (OTP، انتخاب نقش، ساخت باشگاه، تایید دعوت) طبق ساختار Component → Hook → Service → API.
- `features/dashboard/` — سه نوع داشبورد (باشگاه، مربی، ورزشکار)، هرکدام Widget-Based با Loading / Empty / Error State مستقل.
- `features/members/` — مدیریت اعضای باشگاه (دعوت عضو جدید، ویرایش طرح و وضعیت، تعلیق، حذف، جستجو و فیلتر).
- `features/trainers/` — مدیریت مربیان باشگاه (دعوت مربی، تعلیق، حذف، شمارش شاگردان هر مربی).
- `features/messages/` — اینباکس گفتگوی مربی و ورزشکار روی جدول `messages`؛ پیام می‌تواند مستقل باشد یا به یکی از برنامه‌های مشترک گره بخورد (همان پیام‌ها زیر خود برنامه هم دیده می‌شوند).
- `features/revenue/` — دفتر درآمد باشگاه (ثبت شهریه و دریافتی‌ها، ویرایش و حذف، خلاصه و نمودار ماهانه).
- `features/club/` — تنظیمات باشگاه (نام، لوگو، آدرس، تلفن، ساعات کاری) و طرح‌های عضویت اختصاصی هر باشگاه.
- `components/layout/` — Header و Sidebar پویا بر اساس نقش کاربر (اعضای مشترک بین تمام صفحات پنل).
- `components/ui/` — کامپوننت‌های پایه به سبک shadcn/ui.
- `lib/api/` — کلاینت API (توکن نشست، fetch، مدیریت خطا).
- `backend-php/` — API با PHP و MySQL: اسکیما، دیتای اولیه، و کنترلرها. همان دسترسی‌هایی که قبلاً RLS پستگرس بود، اینجا در `src/Acl.php` و کنترلرها صریح بررسی می‌شود.
- `supabase/migrations/` — اسکیمای نسخه‌ی قبلی (پستگرس)، به‌عنوان مرجع تاریخی نگه داشته شده.

## نکات مهم

- تمام داده‌های داشبورد از API خوانده می‌شوند؛ داده Mock وجود ندارد. برای دیدن اطلاعات واقعی، پس از ساخت جدول‌ها چند رکورد نمونه (عضو، مربی، تراکنش درآمد، حضور کلاس) در جداول مربوطه ثبت کنید.
- جهت و زبان پیش‌فرض کل برنامه RTL و فارسی است.
- فونت مورد استفاده Vazirmatn (از طریق `next/font/google`) است.
